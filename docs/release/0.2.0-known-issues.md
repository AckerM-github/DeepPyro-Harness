## 1. 图例与维护规则

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| 严重度 | `S1` | 发布定位或数据风险；不解决就必须在 release note 顶部显式声明，不能静默发布 |
|  | `S2` | 功能缺口或用户可见限制；已有 workaround 或明确的后续版本 |
|  | `S3` | 文档、测试、工程债；不阻塞使用，但会降低可维护性 |
| 状态 | `open` | 仍未完成 |
|  | `partial` | 主体已在 0.2.0 落地，但行内列出的子缺口仍未关闭；子缺口必须写在同一行 |
|  | `accepted` | 有意保留的设计/兼容行为，不是 bug；后续版本可重新评估 |
|  | `resolved` | 已由后续提交解决，保留记录防止重复登记 |
|  | `decision` | 需要发布负责人拍板，未拍板前不能关闭 |

维护规则：

1. **ID 不复用。** 关闭的条目保留原 ID 和 `resolved` 状态；新问题追加新 ID。
2. **一行一件事。** 不要把多个独立缺口塞进同一行；确实同源的用同一行的分号列出。
3. **证据必须可点。** 优先链到代码/文档的具体行；行号会随文档修改漂移，改文档时顺手更新。
4. **摘要不复制整表。** README/release note 只列 S1 和发布必须知道的 3–5 条，其余指回本文。
5. **发布前复核。** 打 tag 前逐行确认 S1 全部有结论、`open`/`partial` 的 S2 在 release note 可见。

## 2. 发布判断（2026-11-18 复核）

- 按当前定位可以发布 **0.2.0 release candidate**：四道门禁绿（ruff、format、pyright 0 new、pytest 全绿），

  usage/trace 有本地记录且 OTLP 可显式开启；memory 工具、live eval、Task/Handoff、capability manifest 已接线。

  `dsh` 字样仍在 `src` 中（KI-032）。

  其余 S1 已无 open 项（KI-002 已 resolved）。
